⚠
This is a live demo against a real cluster. It deletes all app-* indices, invalidates demo-* API keys and removes its watch, mapping and team roles before it runs — and again afterwards unless you ask it to keep them.
  • Use a dedicated, disposable demo cluster only. Never point this at a shared or production cluster.
  • Not a production security configuration: HTTP, a shared HMAC key, a trial licence, and usable bearer tokens are printed on screen.
  • The watcher's API key holds cluster-wide role put/get. Its privileges are not limited to the role names the watch creates.

Walkthrough

    00

    What this demo simulates

    A team must get read access to its own indices without anyone editing a role by hand. The team cannot create roles; a privileged watcher performs that operation. Three moving parts do it.

    (a) A JWT

    Carries a team claim. The realm turns that claim into searchable metadata at login.

    (b) A role mapping with a template

    Resolves team → team_<team>_reader on the fly. No user is listed anywhere.

    (c) A watcher

    Sees new app-<team>-* indices and creates the role body from the index name.

    The app team itself only ever holds create_index + write on app-<team>-*. It can create its own index, and that act alone causes it to gain read access — it can never create a role, and never needs an admin.

    Watch the two privilege hand-offs: the admin sets up (a)(b)(c) once, then the team drives everything itself.

    Live cluster

    Connect to see the cluster this page is about to talk to.

    01

    Admin: mint a minimal API key for the role-creator watcher

    The admin creates one API key that the watcher will use. It can write roles — and nothing else.

    02

    Admin: JWT role mapping — claim team=X → role team_X_reader

    The mapping is what makes this zero-touch. The role name is resolved at login time from a template, so a brand-new team needs no admin edit.

    03

    Admin: install the role-per-team watch

    The watcher is the only thing that ever creates a role, and it does it from index names — app-alpha-orders → team_alpha_reader. The team never names a role; the index name alone decides the role body.

    04

    Admin: onboard teams — each gets a create-index key scoped to app-<team>-*

    This is the whole trust model: the team can create and write its own indices, and that is all. No read, no role verbs, no cluster verbs.

    05

    Team alpha: bootstrap its own index with only the limited key

    The 403s are the point: the team is contained to its own namespace and can never mint itself a role. Its only lever is creating an index — which is exactly the trigger the watcher is waiting for.

    06

    Before the watcher has run, a team-alpha JWT authenticates but sees nothing

    The token is valid and the realm accepts it — the team claim already resolves to team_alpha_reader. The role just doesn't exist yet, so the mapping grants nothing. Authentication and authorisation are separate.

    07

    Wait for the watcher to notice the new index and create the role

    The team never asked for this and never had the privilege to do it. Creating app-alpha-orders was enough: the watcher saw the name, built the role from the name pattern, and the step-2 mapping now has something to point at. This is the self-service loop, fully closed.

    08

    JWT access: alpha token reads alpha data only

    Read its own data: yes. Read another team's data: no. Write: no. The same claim that was refused in step 6 now grants access — the only thing that changed is that the watcher filled in the role body.

    09

    A second team shows it is fully self-service

    Beta onboards itself: own key → own index → watcher → own role. No admin action between alpha and beta. That is what “self-service” means.

    10

    Token hygiene: bad tokens are rejected by the realm

    The claim is not a capability: a valid signature alone grants nothing. gamma has no index, so no watcher-generated role exists, so the mapping resolves to a role that grants nothing.

    11

    What just happened

    1

    The admin did three things once: a role-mapping template, a JWT realm, and a watcher. No user, no role, and no mapping per team.

    2

    The team held one API key: create_index + write on app-<team>-*.

    3

    Creating app-alpha-orders triggered the watcher, which built team_alpha_reader from the index name — a privilege the team did not have and never asked for.

    4

    A JWT with team=alpha then resolved to that role at login, so the team got read access it was never granted directly, while being locked out of every other team's data and of role creation.

    Effective access without effective authority: the team CAN reach its data, but it can never reach the role API that made that possible.
